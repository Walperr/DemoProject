# RegistrationDemo — демо-проект для занятия 1

Простое WPF-приложение «Форма регистрации». Специально без MVVM и без базы данных —
это темы следующих занятий, здесь код-behind, чтобы не отвлекать от темы инструментов.

## Структура

```
RegistrationDemo.sln
RegistrationDemo/              — приложение
  MainWindow.xaml              — форма (Grid: Имя, Email, Дата рождения, кнопка)
  MainWindow.xaml.cs           — код-behind, обработчик кнопки НЕ реализован (см. ниже)
  AgeCalculator.cs             — возраст, категория участника и цена; содержит намеренный баг
  EmailValidator.cs            — проверяет email, ошибок не содержит
RegistrationDemo.Tests/        — тестовый проект (MSTest), уже подключён к решению
  EmailValidatorTests.cs       — 2 готовых теста + 2 заготовки с Assert.Inconclusive
  AgeCalculatorTests.cs        — 5 зелёных тестов + 1 КРАСНЫЙ (он ловит баг из п. 2)
```

Открыть `RegistrationDemo.sln` в Visual Studio — стартовый проект уже настроен,
тесты видны в Test Explorer сразу после открытия решения.

## 2. Баг для демонстрации отладчика

### Что делает код

`AgeCalculator.BuildProfile` — это цепочка из четырёх шагов, и каждый шаг живёт
в отдельном методе:

```
BuildProfile
 ├── CalculateExactAge      → сколько полных лет, месяцев и дней
 ├── DaysUntilNextBirthday  → сколько дней до ближайшего дня рождения
 ├── ResolveTier            → категория участника по таблице Tiers (цикл по диапазонам)
 └── CalculateDiscount      → скидка категории + бонусы, ограничение сверху
                              → и уже из неё считается цена
```

Категории и скидки:

| Категория  | Возраст | Скидка |
|------------|---------|--------|
| Дошкольник | 0–6     | 100%   |
| Школьник   | 7–17    | 50%    |
| Студент    | 18–23   | 30%    |
| Взрослый   | 24–59   | 0%     |
| Пенсионер  | 60+     | 40%    |

Плюс бонусы: +10%, если до дня рождения осталось ≤ 7 дней, и +5% за круглую дату
(20, 30, 40 лет...). Итог ограничен 100%.

### Как воспроизвести баг на паре

Введите в форме дату рождения **1 января года «текущий минус 18»**
(в 2026-м это 01.01.2008 — человеку ровно 18 лет, и это верно в любой день года).

Ожидаем: «категория «Студент», скидка 30%, к оплате 8 400 ₽».
Получим: **«категория «Школьник», скидка 50%, к оплате 6 000 ₽»** — восемнадцатилетний
студент оформляется как школьник.

Второй вариант того же бага: 1 января года «текущий минус 24» — человек должен стать
«Взрослым» без скидки, а получает «Студента» со скидкой 30%.

Тот же баг ловится тестом: в Test Explorer красный
`AgeCalculatorTests.BuildProfile_EighteenYearsOld_IsStudent`, при этом соседний
`BuildProfile_SeventeenYearsOld_IsSchoolboyWithHalfPrice` — зелёный. Отличная затравка
для группы: «почему 17 работает, а 18 — нет?».

### Сценарий разбора у доски

1. **Точка останова** (F9) в `BuildProfile` на строке `ParticipantTier tier = ResolveTier(years);`,
   запуск с отладкой (F5), нажать кнопку на форме.
2. **Локальные переменные / Autos**: `years == 18`. Возраст посчитан ВЕРНО — первое
   подозрение (возраст) снимается, не читая код.
3. **F10 (Step Over) vs F11 (Step Into)**: `CalculateExactAge` перешагиваем — она уже
   проверена, а в `ResolveTier` заходим внутрь. Shift+F11 (Step Out) — как вернуться назад,
   если провалились не туда.
4. **Окно Watch**: добавить `years`, `i`, `lowerBound`, `upperBound`, `Tiers[i]` и целиком
   выражение условия `years >= lowerBound && years <= upperBound`. Пошагово (F10) пройти
   итерации цикла и увидеть, как на `i == 1` (Школьник, границы 7 и 18) условие даёт `true`,
   хотя должно было отдать эту категорию только до 18.
5. **Условная точка останова**: правый клик по точке останова → «Условие» → `i == 1`
   (или `years == 18` в `BuildProfile`) — чтобы не щёлкать F10 по всем итерациям и не
   ловить чужие вызовы.
6. **Стек вызовов**: показать цепочку `SubmitButton_Click → BuildProfile → ResolveTier` —
   симптом виден на форме, а причина двумя кадрами глубже.
7. **Окно «Интерпретация» (Immediate)**: прямо во время паузы вычислить `ResolveTier(17)`,
   `ResolveTier(18)`, `ResolveTier(19)` — граница видна без перезапуска приложения.
8. **Отладка теста**: в Test Explorer правой кнопкой по красному тесту → «Отладить» —
   тот же отладчик, но без кликов по форме.

### Ответ (спойлер для преподавателя)

`AgeCalculator.ResolveTier`, строка условия:

```csharp
if (years >= lowerBound && years <= upperBound)   // ← верхняя граница должна быть строгой
```

Верхняя граница диапазона — это нижняя граница СЛЕДУЮЩЕЙ категории, то есть она
уже не принадлежит текущей. Из-за `<=` диапазоны перекрываются в одной точке, и
пограничные возрасты (7, 18, 24, 60) достаются предыдущей, более «дешёвой» категории.
Правильно:

```csharp
if (years >= lowerBound && years < upperBound)
```

После правки красный тест зеленеет. Хорошее место, чтобы показать Edit & Continue:
поправить символ прямо во время паузы и продолжить выполнение без перезапуска.

### Бонус: демонстрация отладки исключений

Если нужен второй заход — уже про падения, а не про неверный результат — временно
замените тело `DaysUntilNextBirthday` на «наивную» версию:

```csharp
DateTime anniversary = new DateTime(today.Year, birthDate.Month, birthDate.Day);
if (anniversary < today)
    anniversary = anniversary.AddYears(1);
return (anniversary - today).Days;
```

Теперь дата рождения **29 февраля** роняет приложение с `ArgumentOutOfRangeException`
в невисокосный год — можно показать всплывающее окно исключения, стек вызовов,
просмотр значений в кадре с ошибкой и настройку «Исключения» (Ctrl+Alt+E) для остановки
в момент выброса. Тест `CalculateAge_BornOnLeapDay_ReturnsFullYears` при этом остаётся
зелёным (он не трогает этот метод) — повод поговорить о том, что тесты покрывают не всё.

## 3. Логика для unit-тестов

`EmailValidator.IsValid` — чистая, детерминированная функция без побочных эффектов,
удобно тестировать. В `EmailValidatorTests.cs` уже есть два готовых теста как пример
паттерна Arrange/Act/Assert и два теста-заготовки (помечены `Assert.Inconclusive`,
видны в Test Explorer жёлтым, а не зелёным) — можно дописать их вместе со студентами.

`AgeCalculatorTests.cs` показывает второй важный приём: «сегодняшняя дата» передаётся
в расчёт параметром (`BuildProfile(birthDate, today)`), поэтому тесты не зависят от дня
запуска. Стоит проговорить это отдельно — типовая причина «мигающих» тестов.
